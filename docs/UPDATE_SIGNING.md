# Update signing (one-time setup and every release)

The game installs updates itself (see `docs/UPDATE_CHECK.md`), but only an installer that carries a
valid signature from **your** private key. The game contains just the public key, so nobody who
gains access to the GitHub repo or a release can make players install something else. This is a
separate mechanism from Windows code signing (Authenticode), which this project does not use.

Until a public key is built in, the game does **not** install updates itself: the notice keeps its
plain Download button.

> **Status: signing is on with a SigningKeyMaker key (RSA-3072).** `PUBLIC_KEY_PEMS` in `run/update_verifier.gd` holds the public halves of **two** keys generated by SigningKeyMaker: the main key (first), which signs every release, and an offline **backup key** (second), used only for recovery (see the last section). The game accepts a signature from either. Each private key is a `signing-private.pfx`, passphrase-protected. For each release set `UPDATE_SIGNING_KEY` to the **.pfx** path and `UPDATE_SIGNING_PASS` to its passphrase: `scripts/build_installer.ps1` signs in memory with .NET (the private key is loaded ephemerally and never written to disk, not even as a temporary PEM), then verifies the signature with OpenSSL against the embedded public keys (it reports which one matched). Installs older than the first release carrying this key (v0.5.x and earlier) cannot verify it and must update once by hand. The OpenSSL-only setup below still works if you prefer a `.pem` private key.

## One-time setup

The easy way: open a normal **Windows PowerShell window** (Start menu, not an editor or assistant
prompt) and run

```powershell
powershell -ExecutionPolicy Bypass -File scripts/make_signing_key.ps1
```

It creates the pair in `%TEMP%\signing`, tests that a signature made with the private key verifies
with the public one, and prints a random passphrase once for you to save (add `-Prompt` to type your
own instead). Then continue at step 3 below.

To do it by hand instead, run these in PowerShell or Git Bash (OpenSSL ships with Git for Windows in
`C:\Program Files\Git\usr\bin`), in a temporary folder, not in the repo.

```powershell
mkdir $env:TEMP\signing; cd $env:TEMP\signing
$openssl = "C:\Program Files\Git\usr\bin\openssl.exe"

# The passphrase is passed through an environment variable of this window only: the OpenSSL that
# ships with Git often cannot read its own hidden prompt from PowerShell.
$s = Read-Host "Choose a passphrase" -AsSecureString
$env:KEYPASS = [System.Net.NetworkCredential]::new('', $s).Password

# 1. Create a passphrase-protected 4096-bit RSA key.
& $openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:4096 -aes-256-cbc -pass env:KEYPASS -out update_signing_private.pem

# 2. Derive the public key.
& $openssl pkey -in update_signing_private.pem -passin env:KEYPASS -pubout -out update_signing_public.pem

Remove-Item Env:KEYPASS
```

(In Git Bash the plain commands work and prompt for the passphrase: drop the `-pass`/`-passin` options.)

3. **Store the private key in your password manager**: attach `update_signing_private.pem` to a
   secure note and keep the passphrase in the same entry (or a separate one). Make a second copy of
   the encrypted file somewhere offline, such as a USB stick in a drawer. Then delete the
   `update_signing_private.pem` file from the temporary folder. **Never commit it, and never paste it
   into a chat or issue.**
4. The public key is not secret. Put it in `run/update_verifier.gd` as the value of
   `PUBLIC_KEY_PEMS` (one entry per key: the whole `-----BEGIN PUBLIC KEY-----` ... `-----END PUBLIC KEY-----` block, as a
   `"""` multi-line string), commit it and release a version that contains it. Installs older than
   that version have no key, so they update once by the normal download; after that updates are
   in-game.

## Every release

The short way (works with the `.pfx` or a `.pem` key): bump `config/version`, merge to `main`, then in a normal PowerShell window

```powershell
# Once: replace <YOUR-KEY-PATH> with the real location of your signing-private.pfx (a path that exists on
# this machine), then open a NEW window so it takes effect. Do not paste this line unchanged.
setx UPDATE_SIGNING_KEY "<YOUR-KEY-PATH>"
Test-Path $env:UPDATE_SIGNING_KEY    # in the new window: must print True

powershell -ExecutionPolicy Bypass -File scripts\release.ps1 -Publish
```

If the saved path is wrong or the window is older than the `setx`, the script stops at once with "Signing key not found" and shows the path it tried. You can also skip the variable and pass the path for one run: `scripts\release.ps1 -Publish -KeyPath "<YOUR-KEY-PATH>"`.

`scripts/release.ps1` checks that you are on an up-to-date `main` with a free tag, runs the full `scripts/check.ps1`, confirms the GitHub Actions run on that commit is green, finds Godot, asks for the passphrase, builds and signs, clears the passphrase, and asks before running `gh release create`, which makes a **draft** release: review it on GitHub and click Publish release (players, and the in-game updater, only see it then). Release checklist item: the installer must be under 150 MiB while v0.8.2 clients exist (they carry the old download cap); `build_installer.ps1` fails above it and `release.ps1` prints the margin to the old and the current cap. Add `-NoDraft` to publish immediately. Leave out `-Publish` to build only. The manual steps below do the same by hand.

1. Take `update_signing_private.pem` out of the password manager into a temporary folder.
2. In PowerShell:

```powershell
$env:UPDATE_SIGNING_KEY = '<PATH-TO-YOUR-KEY-FILE>'   # the real path of the .pem or .pfx
$s = Read-Host "Key passphrase" -AsSecureString
$env:UPDATE_SIGNING_PASS = [System.Net.NetworkCredential]::new('', $s).Password
powershell -ExecutionPolicy Bypass -File scripts\build_installer.ps1
```

   If `UPDATE_SIGNING_PASS` is not set, OpenSSL asks for the passphrase itself, which works in Git Bash
   but not in every PowerShell host.

   The script exports the game, builds the installer, writes `.sha256`, writes and signs the update
   manifest (`.manifest` and `.manifest.sig`, see `docs/UPDATE_CHECK.md`), and
   checks the signature against the public key in `run/update_verifier.gd` before finishing. It refuses to start if a public key is built in but `UPDATE_SIGNING_KEY` is
   missing.
3. Delete the temporary private key file and clear the variables (`Remove-Item Env:UPDATE_SIGNING_KEY, Env:UPDATE_SIGNING_PASS`).
4. Publish all four files in the release (the game downloads the `.manifest` and `.manifest.sig`). From v0.6.5 the
   legacy `.sig` (a signature over the bare installer, read only by v0.6.1 and earlier) is no longer published, so
   those builds must be updated by hand:

```powershell
gh release create v<version> build\TheUnforgotten-Setup-<version>.exe build\TheUnforgotten-Setup-<version>.exe.sha256 build\TheUnforgotten-Setup-<version>.exe.manifest build\TheUnforgotten-Setup-<version>.exe.manifest.sig
```

### Check the release before players can get it

`scripts/release.ps1` pins the release to the commit it built (`--target <sha>`), and then checks what GitHub
actually serves with `scripts/verify_release.ps1`: it downloads the four assets, recomputes the installer's
SHA-256, compares it with the `.sha256` file and the manifest, checks that the manifest is exactly the text the
signer writes, and verifies `.manifest.sig` with OpenSSL against the public keys in `run/update_verifier.gd`
(the same check `build_installer.ps1` does). It prints PASS or FAIL per check and exits 1 on any failure.

- After `-NoDraft` it runs by itself; if it fails, take the release down at once (`gh release edit v<version> --draft`).
- For a **draft** (the default), run it **before clicking Publish release**:
  `powershell -ExecutionPolicy Bypass -File scripts\verify_release.ps1 -Version <version> -Draft`
  It needs `gh auth login` (drafts are private). Run without `-Draft` for a published release, or with
  `-LocalDir build` to check the files on disk.

### If a release fails halfway

`gh release create` makes the draft first and then uploads the four files. If the upload fails (network, rate limit,
closed laptop) you can be left with a **draft that has some or none of the files**.

1. Do not click Publish on it. Players cannot see a draft, and the updater needs all four files.
2. Rerun `scripts\release.ps1 -Publish -ReplaceDraft`. It notices the draft of the same tag, asks before deleting it
   (`gh release delete v<version> --yes`) and then creates a fresh one. Without `-ReplaceDraft` it stops and tells you
   instead of guessing. The script refuses outright if the tag is already published or the tag already exists on
   origin; bump `config/version` in that case.
3. By hand: `gh release list` shows drafts, `gh release delete v<version> --yes` removes one (add `--cleanup-tag`
   only if a stray tag was created), and `gh release upload v<version> <file>... --clobber` can add the missing files
   to a draft you want to keep. Either way finish with `verify_release.ps1 -Draft` before publishing.
4. A release published without all four files is simply not installable in-game; take it back to a draft
   (`gh release edit v<version> --draft`), fix it, verify, publish again.

A release without the `.manifest` and `.manifest.sig` is simply not installable in-game: the update fails with a message and
the bar falls back to the Download button.

## If the key is lost or exposed

The backup key exists for this. Keep its private `.pfx` **offline** (a USB stick, not the same place as
the main key) and its passphrase somewhere different from the main key's. It signs nothing day to day.
Installs trust only the keys built into their own version, so the backup protects installs of the
version that first embedded it and every later one (v0.6.3 and up); older installs depend on the main
key alone.

- **Main key lost** (no copy left, or the passphrase is forgotten): sign the next release with the
  backup key instead. Set `UPDATE_SIGNING_KEY` to the backup `.pfx` and `UPDATE_SIGNING_PASS` to its
  passphrase and run `scripts\release.ps1 -Publish` as usual. Installs that trust the backup key update
  in-game. In that same release, generate a new backup key and a new main key and replace the lost one in
  `PUBLIC_KEY_PEMS`, so you are not left with a single key.
- **Main key exposed** (someone else may hold the key and its passphrase): until installs stop trusting
  it, that person can sign an update every install will accept. Act quickly:
  1. Generate a new key pair (SigningKeyMaker).
  2. Make a release signed with the **backup** key whose `PUBLIC_KEY_PEMS` **drops the leaked key** and
     adds the new one. Installs that update to it no longer trust the leaked key.
  3. Tell players to update promptly and not to install anything from an unexpected source. Installs
     that never update keep trusting the leaked key.
- **Backup key lost or exposed**: replace it in the next normal release (sign with the main key, swap the
  backup entry in `PUBLIC_KEY_PEMS`), and generate and store a fresh backup.
- **Both lost**: installed games cannot verify anything signed by a new key. Generate new keys, embed
  them, release it, and tell players to reinstall once by hand from the releases page.

Rotating a key means a new release, which always needs signing: only ever remove a key from
`PUBLIC_KEY_PEMS` in a release signed by a key that stays in it.
